# SPRINT-013 — Observability & Alerting

**Status:** In progress — repository implementation complete; target validation pending

**Classification:** Platform Capability

**Phase:** Phase 2 — Shared Platform Capabilities

**Selected Technology:** Grafana Alloy, Prometheus, Loki and Grafana

**Primary Focus:** Actionable platform health, storage visibility and operational alerting

**Last Reviewed:** 2026-08-11

---

## Objective

Introduce a small, reusable observability capability that answers whether
HomeLab07 is healthy, detects actionable degradation and preserves enough
short-lived evidence to diagnose it.

The Sprint establishes a baseline rather than a complete monitoring product.
It prioritizes host and storage health, service availability, platform
operations and selected diagnostic logs without introducing public exposure,
Docker daemon access or unnecessary exporters.

## Architecture decision

HomeLab07 will use one collector, one metrics store, one log store and one user
interface:

```text
                         LAN operators
                              |
                         Grafana :3000
                         /           \
                  Prometheus         Loki
                       ^               ^
                       |               |
                    Grafana Alloy -----+
                  /       |       \
             host     probes     selected logs
           metrics       |       and journal
                         |
                  service endpoints

              HomeLab07 Operation Layer
           backup / security scan / platform
                         |
                  atomic *.prom files
                         |
                       Alloy

                       Rockstor
             authoritative storage management
                         |
              read-only storage metrics adapter
                         |
                  atomic rockstor.prom
```

The four baseline services are:

- `homelab07-alloy`
- `homelab07-prometheus`
- `homelab07-loki`
- `homelab07-grafana`

Alertmanager, cAdvisor, Pushgateway, Netdata, standalone node exporter and
database-specific exporters are not part of the baseline. A standalone
Blackbox Exporter is introduced only if target validation proves that Alloy's
embedded blackbox exporter cannot provide the required HTTP and TLS probes
cleanly.

Primary implementation references:

- [Grafana Alloy Unix exporter](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.exporter.unix/)
- [Grafana Alloy blackbox exporter](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.exporter.blackbox/)
- [Grafana Alloy journal source](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.journal/)
- [Prometheus node exporter textfile collector](https://github.com/prometheus/node_exporter#textfile-collector)
- [Loki log retention](https://grafana.com/docs/loki/latest/operations/storage/retention/)
- [Grafana provisioning](https://grafana.com/docs/grafana/latest/administration/provisioning/)
- [Rockstor pool and share implementation](https://forum.rockstor.com/t/internal-implementation-of-pools-shares-snapshots-and-clones/453)

## Decision principles

- Observe platform capabilities before collecting application-specific detail.
- Alert only when an operator can take a documented action.
- Prefer native and read-only sources over privileged access.
- Keep labels bounded, anonymous and independent of environment-specific names.
- Treat metrics and logs as disposable operational data, not business records.
- Provision datasources, dashboards, rules and collector configuration from Git.
- Keep production and Rockstor management interfaces as operational sources of
  truth; observability provides history, correlation and notification.

## Scope

### Included

- Linux host CPU, load, memory, swap, filesystem, inode, network and uptime
  metrics through Alloy's Unix exporter integration.
- HTTP, TLS and latency probes for an explicitly approved service inventory.
- Prometheus-compatible metrics generated by HomeLab07 operation scripts.
- Read-only Rockstor/Btrfs health and mount metrics through a host-side adapter.
- Selected journald entries and explicitly approved log files.
- Nginx Proxy Manager access/error log evaluation as the initial shared HTTP
  observation point, subject to path and redaction validation.
- Prometheus metrics retention and Loki log retention.
- Three provisioned dashboards: Platform Overview, Applications and Operations.
- A small, actionable alert baseline with one alert owner.
- LAN-only Grafana access from any device on the configured private LAN.
- Private configuration examples and operation-layer lifecycle integration.
- Runbooks, validation evidence and rollback procedures.

### Excluded

- Public, Cloudflare or Internet publication of Grafana, Prometheus, Loki or
  Alloy.
- Scraping the Rockstor HTML interface, internal WebSocket feeds or an
  undocumented API.
- Docker socket access or mounting `/var/lib/docker` into Alloy.
- Privileged observability containers.
- Full distributed Loki, long-term metrics storage or high availability.
- Application performance monitoring, traces and per-user analytics.
- Automatic remediation or container restart.
- Logging request bodies, credentials, authorization headers, session tokens,
  query strings, usernames or document/file names.
- Installing Netdata or Scrutiny as a duplicate monitoring stack.
- Backing up Prometheus samples, Loki chunks or disposable Alloy caches.
- Keycloak SSO for Grafana during the baseline.

## Network and access contract

Prometheus, Loki and Alloy join only the internal observability paths required
for collection and publish no host ports. Grafana is the only host-accessible
service.

Grafana administration must use an explicit private host bind address supplied
through private configuration, following the same LAN-only policy used for the
Nginx Proxy Manager administration interface. A wildcard bind such as
`0.0.0.0:3000` or `[::]:3000` is rejected.

The intended contract is:

```text
<private-LAN-host-address>:<configured-port>:3000
```

The router must not forward that port. Any device already permitted on the
private LAN may access Grafana; guest, untrusted and WAN network separation
remains an external network-control responsibility and must be validated.

Grafana uses a local emergency administrator during Sprint 013. Keycloak
integration is a future enhancement after LAN access, recovery and alerting are
stable.

## Collection model

### Host metrics

Alloy uses `prometheus.exporter.unix` with only the collectors needed for:

- CPU and sustained load;
- memory and swap pressure;
- filesystem capacity and availability;
- inode availability;
- network throughput and errors;
- host uptime.

Any host `/proc`, `/sys` or root filesystem view required by the collector is
mounted read-only and narrowly. Alloy remains unprivileged and receives no
Docker daemon access.

### Service availability

Running container state is not sufficient evidence of service availability.
The baseline validates approved endpoints through HTTP/TLS probes and records:

- successful response or approved redirect;
- TLS validity and certificate expiry;
- response latency;
- probe failure duration.

Probe targets and expected status behavior are private configuration. Real
hostnames, addresses and certificates never enter the repository or metric
labels. Internal MariaDB and Valkey reachability is checked without publishing
either service.

### Operation-layer metrics

Batch operations write Prometheus text files beneath a private, pre-created
metrics root configured by `HOMELAB07_OBSERVABILITY_METRICS_ROOT`.

Alloy consumes this directory through the textfile collector provided by its
embedded `prometheus.exporter.unix` component. It exposes the parsed samples for
Prometheus scraping; Sprint 013 introduces neither a standalone node exporter
process nor a custom `.prom` parser. The metrics root is mounted read-only into
Alloy and configured as the only approved textfile collector directory.

Initial files are:

```text
backup.prom
security.prom
platform.prom
rockstor.prom
```

Writers create an owner-controlled temporary file on the same filesystem,
validate its syntax and atomically rename it over the final file. Interrupted
operations must not leave a partially written metric. Metrics record status,
timestamps, duration and bounded counts; they never contain paths, snapshot
identifiers, filenames, detected secret content or personal identities.

### Batch metric freshness contract

Every batch producer must publish, at minimum, three semantic metrics using its
own bounded prefix:

```text
<job>_last_run_timestamp_seconds
<job>_last_success_timestamp_seconds
<job>_last_status
```

`last_run_timestamp` records the most recent completed attempt, whether it
succeeded or failed. `last_success_timestamp` changes only after a successful
operation. `last_status` is `1` for the latest successful completed attempt and
`0` for the latest failed completed attempt. A job that terminates before it can
publish retains the preceding values and is detected by their age.

Alerts and dashboards must evaluate both status and freshness. A value of
`last_status 1` is never sufficient evidence of current health. Each job has a
configurable maximum age, and the absence of any required metric is an unknown
or failing state rather than success. The textfile collector's file modification
metric may be used to detect ingestion or writer failures, but it does not
replace the job-owned run and success timestamps.

Initial operation metrics include:

- latest successful backup timestamp, status and duration;
- latest security-scan timestamp, status and sanitized severity counts;
- Gitleaks finding count without matched content;
- platform audit status;
- expected service inventory and operation-script health.

The Operation Layer remains functional when observability is stopped. Failure
to publish a metric must not turn a successful backup into a failed recovery
point; the metric publication failure is reported separately and exits
according to the documented operation contract.

## Rockstor integration

Rockstor remains authoritative for storage configuration, pools, shares,
snapshots, SMART operations and interactive diagnosis. Sprint 013 does not
replace its dashboard or depend on internal dashboard feeds.

A fixed host-side, read-only adapter obtains the minimum storage evidence using
supported host facilities such as:

- `findmnt` for expected mount identity and filesystem type;
- `btrfs filesystem usage` for data and metadata pressure;
- `btrfs device stats` for read, write, flush and corruption errors;
- `btrfs scrub status` for scrub result and age;
- read-only mount-state inspection;
- SMART health and temperature only when a reliable, bounded source is
  validated.

The adapter must distinguish an existing directory from a correctly mounted
Rockstor share. A missing share mount can otherwise leave a valid directory on
the host filesystem and create a false healthy result.

Alloy is not granted root or Btrfs administration privileges. If a metric needs
elevation, a root-owned systemd service and timer invokes one fixed wrapper with
read-only commands and writes `rockstor.prom` into the metrics root. Any sudo
rule is limited to that wrapper and is documented; arbitrary command execution
is prohibited.

Expected mounts, thresholds and stable storage aliases belong in
`HomeLab07.private/`. Metrics use abstract aliases such as `platform-data` or
`backup`, never real share names, device serial numbers, UUIDs or paths.

Initial Rockstor metrics cover:

- expected share mounted: `1` or `0`;
- expected Btrfs filesystem: `1` or `0`;
- filesystem read-only state;
- Btrfs data and metadata usage percentage;
- cumulative device error counters;
- last scrub status and age;
- SMART overall health and temperature only if validated.

Per-share logical consumption is not an initial alert source because Btrfs
snapshots, reflinks and quota groups can make naive accounting misleading.

Rockstor-native SMART and scrub notifications remain enabled where available.
Rockstor owns storage-device and scrub diagnosis; Grafana owns platform
correlation, capacity, expected-mount, stale-operation and notification views.
Duplicate notifications are reviewed before enablement.

## Log contract

Loki is diagnostic support, not an audit archive.

Alloy may read:

- explicitly selected host journal units;
- explicit read-only log paths whose ownership and rotation are understood;
- Nginx Proxy Manager logs as the initial shared source for HTTP status classes
  and proxy failures.

A service is not marked as log-covered until target validation proves its
source, permissions, rotation and redaction behavior. Application logs that
exist only through the Docker logging driver remain excluded until a safe
source is designed.

Before ingestion, the pipeline drops or redacts sensitive fields. High-cardinality
values such as full URL, query string, client address, user, file, request ID or
token must not become Loki labels. Labels are limited to stable dimensions such
as platform, service, environment class, severity and status class.

## Data and storage lifecycle

Persistent runtime roots are separate:

```text
observability/
├── prometheus/
├── loki/
├── grafana/
└── alloy/
```

Initial retention targets are:

- Prometheus: 15 days;
- Loki: 7 days;
- Alloy checkpoints: only what is required to resume collection.

Retention and size limits are configured explicitly and adjusted only from
measured target-host consumption. Loki runs in single-binary mode with its
compactor retention configured. Anonymous usage reporting is disabled where
supported.

Prometheus data, Loki data and Alloy cache/checkpoints are reproducible and are
not included in platform recovery backups. Repository configuration,
provisioned dashboards, datasource definitions, alert rules and runbooks are
the recovery source of truth. Grafana UI state is minimized; any unavoidable
local administrative state and its recovery decision must be documented before
Sprint closure.

## Dashboards

### Platform Overview

Answers “Is HomeLab07 healthy?” within approximately ten seconds:

- host CPU, load, memory and swap;
- filesystem and inode pressure;
- network health;
- expected mount and Btrfs state;
- approved services up/down and latency;
- active actionable alerts;
- age and state of the latest backup and security scan.

### Applications

Provides one bounded row or section per approved application:

- availability and response time;
- approved HTTP status classes from the shared proxy;
- restart evidence only if a safe source exists;
- links to filtered, redacted diagnostic logs;
- dependency state relevant to diagnosis.

It must not imply application instrumentation that has not been implemented.

### Operations

Shows:

- backup success, age and duration;
- vulnerability and Gitleaks scan success and age;
- sanitized high and critical finding counts;
- platform policy-audit state;
- certificate expiry;
- Rockstor capacity, errors and scrub freshness.

## Alerting policy

Grafana Alerting is the single alert owner for the baseline. Prometheus stores
metrics and Loki stores logs; neither introduces an independent notification
path during this Sprint. Alertmanager is reconsidered only if a demonstrated
routing or availability requirement cannot be met cleanly.

The initial baseline is limited to approximately 10–12 actionable conditions:

1. Approved service endpoint unavailable for a sustained interval.
2. Keycloak unavailable.
3. MariaDB unavailable.
4. Valkey unavailable.
5. Expected Rockstor share not mounted or mounted with the wrong filesystem.
6. Btrfs read-only state or increasing device error counters.
7. Filesystem, Btrfs metadata or inode pressure above configurable thresholds.
8. Latest backup status failed, its last run is stale or its last success is
   older than the approved recovery objective.
9. Security scan status failed, its last run is stale or its last success is
   older than the approved scan interval.
10. Gitleaks reports one or more findings.
11. Certificate approaches configurable expiry thresholds.
12. Sustained host memory, swap or CPU pressure.

Warning and critical capacity defaults begin at 80% and 90%, respectively, but
must remain configurable and must be validated against Btrfs behavior before
enforcement. Alerts include a runbook link, current state and abstract service
alias. They do not include private endpoints, addresses, usernames, paths or
log excerpts.

Email is the initial notification channel if private SMTP configuration is
available and target validation succeeds. Credentials and recipients remain
outside Git. Alert evaluation is still useful in Grafana when email is not yet
configured, but notification delivery must not be claimed as complete.

## Security contract

- No component runs privileged or mounts the Docker socket.
- No observability component is Internet-accessible.
- Grafana binds only to the configured private LAN host address.
- Prometheus, Loki and Alloy publish no host ports.
- Container references use reviewed patch versions and immutable manifest
  digests before deployment; a patch tag alone is version-pinned, not immutable.
- Secrets and environment-specific values remain in `HomeLab07.private/` with
  owner-only permissions.
- Read-only collection mounts are explicit and minimal.
- Default credentials are prohibited.
- Datasource credentials use least privilege and are not embedded in dashboards.
- Metrics, labels, dashboards and alerts contain no personal or secret data.
- Logs are filtered before persistence and have bounded retention.
- Grafana plugins are not installed unless explicitly approved and pinned.

## Implementation sequence

1. Discover target-host Linux, journald, Rockstor/Btrfs and log-source behavior.
2. Define private storage roots, metrics root, LAN bind and probe inventory.
3. Pin and record immutable image identities for all four services.
4. Deploy Prometheus and Loki internally with explicit retention and limits.
5. Deploy Alloy with host metrics, atomic textfile collection and approved
   read-only sources.
6. Implement and validate the Rockstor adapter without granting Alloy elevated
   privileges.
7. Deploy Grafana on the explicit LAN address and provision datasources.
8. Add approved service probes, using embedded Alloy blackbox functionality or
   a justified standalone exporter.
9. Add selected redacted logs and prove label cardinality remains bounded.
10. Provision the three dashboards and the minimal alert set.
11. Add operation-layer metrics without weakening backup or scan correctness.
12. Validate alert firing, recovery, retention, LAN/WAN boundaries and rollback.

## Validation requirements

### Static validation

- Every Compose definition renders successfully.
- YAML, Alloy configuration and provisioning files parse successfully.
- Shell scripts pass `bash -n` and ShellCheck when available.
- Repository examples contain only placeholders.
- No secret, production address, domain, path or identity is tracked.
- Every runtime image has a reviewed patch tag and immutable digest.

### Runtime validation

- All four baseline services are healthy or report their documented readiness.
- Only Grafana has a host port and it is bound to the configured LAN address.
- No wildcard Grafana bind, privileged mode or Docker socket exists.
- Prometheus and Loki are unreachable directly from the host/WAN boundary.
- A LAN client can access Grafana; an external client cannot.
- Grafana datasources and dashboards appear after clean recreation without UI
  configuration.
- Host, operation and Rockstor metrics are present and recent.
- Alloy's embedded Unix exporter textfile collector parses all four approved
  `.prom` files without a standalone node exporter or custom parser.
- Every batch metric set contains last-run, last-success and last-status, and
  missing or stale metrics are treated as unhealthy or unknown.
- Atomic writer interruption preserves the previous valid metric file.
- A missing expected mount is detected even when its directory still exists.
- Btrfs error, scrub and capacity metrics match sanitized host observations.
- HTTP/TLS probes distinguish runtime state from endpoint availability.
- Approved logs arrive without forbidden fields or unbounded labels.
- Retention and storage size limits are active.
- Stopping observability does not interrupt any platform application or
  operation script.

### Alert validation

- At least one service-down, stale-operation, capacity/mount and certificate
  alert is exercised safely.
- Warning, pending, firing and resolved states behave as documented.
- Notifications contain no environment-specific or sensitive detail.
- Every alert references a repository runbook.
- Only Grafana owns notification delivery.

### Recovery and rollback validation

- Recreating the stack from repository configuration restores datasources,
  dashboards and rules without restoring metrics or logs.
- Rollback stops and removes only observability containers and their host-port
  mapping.
- Runtime data may be retained or removed through an explicit reviewed action;
  rollback never deletes it implicitly.
- Existing applications, Rockstor, backup and vulnerability management continue
  operating after rollback.

## Acceptance criteria

- The four-service baseline is reproducible through the Operation Layer.
- Grafana is accessible from the approved LAN and not from the Internet.
- No wildcard Grafana bind, public Prometheus/Loki port, privileged container or
  Docker socket is introduced.
- Platform Overview reports host, storage, service and operation health.
- Rockstor remains authoritative and is observed without scraping internal UI
  or undocumented feeds.
- A missing or incorrectly mounted expected share produces actionable evidence.
- Backup and security scan scripts publish sanitized metrics atomically.
- Every batch producer publishes the required run, success and status metrics;
  alert health is derived from age and status together.
- HTTP/TLS probes validate actual service behavior rather than container state.
- Loki stores only explicitly approved, filtered and short-lived logs.
- Dashboards, datasources and alert rules are declaratively provisioned.
- The minimal alert set is actionable, references runbooks and has one
  notification owner.
- Retention limits protect the Rockstor storage platform from unbounded growth.
- Observability failure cannot stop or modify the monitored platform.
- Documentation and sanitized target-host evidence complete the implementation.

## Closure evidence

- Sanitized Compose render, service status and immutable image identities.
- Host-port and LAN/WAN access validation.
- Proof of absence of privileged mode and Docker socket mounts.
- Screenshot or export of the three provisioned dashboards with private values
  removed.
- Sanitized metric target and ingestion status.
- Rockstor/Btrfs adapter comparison against read-only host commands.
- Atomic metric-write failure test.
- Selected log redaction and label-cardinality review.
- Alert firing, notification and resolution evidence.
- Retention configuration and measured initial storage consumption.
- Clean recreation and rollback results.
